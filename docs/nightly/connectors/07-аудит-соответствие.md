### Четыре принятые находки плана 06

**1. Селектор в `ConnectorView` возвращает плоский `number[]` — ВЫПОЛНЕНО.**

`ConnectorView.tsx:75-79`:

```ts
const points = useBoardStore(
  useShallow((state): number[] | null =>
    state.document ? connectorPoints(node, state.document) : null,

```

Тип возврата — `number[] | null`, объекта `Route` из плана 04 нет нигде.
Проверил по `node_modules/zustand/vanilla/shallow.js`: два массива проходят
`isIterable` → `hasIterableEntries` (`"entries" in []` истинно из-за
`Array.prototype.entries`) → `compareEntries`, то есть поэлементное сравнение
по индексам. Цикла перерендеров, которого боялась проверка плана, нет.
`shallow(null, null)` уходит в `Object.is` и даёт `true` — вырожденный случай
тоже не зацикливается.

`bezier` выведен из режима, а не из подписки (`routing.ts:216-220`,
`isBezier`), касательные — из самих точек (`labelPosition.ts:100-119`).
Ровно то, что предписывал план 06, пункт 1, включая мотивировку —
она даже дословно перенесена в комментарий `routing.ts:8-11`.

Сопутствующее: `memo` на компоненте (`ConnectorView.tsx:175`), хук стоит

**2. Ветка «спиной к спине» — ВЫПОЛНЕНО.**

Реализована не как четвёртая ветка, а через различение по **знаку**,

`routing.ts:121-122`:


**4. Наконечники берут угол из касательной маршрута — ВЫПОЛНЕНО.**

### 2. Зеркальное вырождение ветки обхода — тот же дефект, что чинили, с другой стороны

План 06, п. 4 переписал ветку обхода из-за случая «`s1.y == s2.y` —
поперечный сегмент нулевой». Для горизонтальных нормалей это исправлено.
Для **вертикальных** нормалей и для горизонтальных при совпавших `x`
вырождение осталось — только теперь оно даёт не проход сквозь фигуру,
а самопересечение с холостым хвостом.

Прогон, четыре достижимые конфигурации (фигуры 100×60):

```
right/right, друг под другом  (100,30) → (116,30) → (116,-16) → (116,-16) → (116,230) → (100,230)
top/top, рядом                (50,0)  → (50,-16) → (-16,-16) → (-16,-16) → (450,-16) → (450,0)
bottom/bottom, рядом          (50,60) → (50,76)  → (-16,76)  → (-16,76)  → (450,76)  → (450,60)
left/left, друг под другом    (0,30)  → (-16,30) → (-16,-16) → (-16,-16) → (-16,230) → (0,230)
```

В каждом — пара совпавших точек (сегмент нулевой длины) и отрезок, который
уходит наружу и тут же возвращается по себе. В случае `top/top` линия сначала
идёт влево до `x = -16`, а потом вправо до `x = 450`: первые 66 единиц пути
нарисованы дважды, и слева от левой фигуры торчит хвост.

Причина видна в `routing.ts:161`: точки `{x: across, y: s1.y}` и
`{x: across, y: s2.y}` совпадают, когда `s1.y === s2.y`, и весь заход
на `across` становится холостым. Правильный маршрут здесь —
просто `(50,0) → (50,-16) → (450,-16) → (450,0)`.

Критерий 2 это **пропускает**: все сегменты ортогональны, включая нулевые.
Тест «сонаправленные вертикально» (`routing.test.ts:53`) существует, но
проверяет ровно ортогональность и на хвост не смотрит. То есть повторилась
ситуация, которую проверка плана описала дословно: «критерий 2 это пропустит».

Не блокирующее — фигура не перечёркнута, приложение не падает. Но это
косметика, видимая с первого взгляда, в конфигурации «два блока рядом,
линия сверху», которая на диаграммах встречается постоянно.

02, блокирующий п. 2, требовал явной ветки разворота «и в перпендикулярной
ветке, когда угол оказывается позади вылета». В планах 04 и 06 этот кусок
замечания не значится ни в «Принято», ни в «Отклонено» — исчез молча.
Проверка плана (05, п. 3) это заметила и переоткрыла, но плана 06 хватило
только на «спиной к спине».

`routing.ts:113-116` считает угол как пересечение лучей безусловно. Прогон,
A(400,0) сторона `right`, B(0,300) сторона `top`:

```
(500,30) → (516,30) → (50,30) → (50,284) → (50,300)
```

Второй сегмент идёт от `x = 516` влево до `x = 50` по `y = 30` — то есть
насквозь через фигуру A (она занимает `x ∈ [400,500]`, `y ∈ [0,60]`) и
поверх собственного вылета. Тот же эффект в мягкой форме при
A(0,0) `right` → B(50,200) `top`:

```
(100,30) → (116,30) → (100,30) → (100,184) → (100,200)
```

Вылет длиной 16 нарисован и тут же стёрт возвратом.

Критерии 2 и 3 оба проходят: сегменты ортогональны, первый сегмент
перпендикулярен стороне. Тестов на перпендикулярную ветку с «углом позади»
нет — все четыре перпендикулярных кейса в `routing.test.ts` подобраны
так, что угол оказывается впереди.

### 4. Правила вычистки маршрута нет (02, п. 14; 05, п. 7)

Ревьюер геометрии просил общее правило: перед возвратом схлопывать
совпадающие соседние точки и сливать коллинеарные сегменты. В план оно
не попало и в код не попало.

Следствия видны в прогонах: `same-line` (right→left на одной высоте) даёт
`(100,30) → (116,30) → (250,30) → (250,30) → (384,30) → (400,30)` — шесть
точек на одной прямой, включая дубль; перпендикулярная ветка даёт
коллинеарную тройку `(100,30) → (116,30) → (450,30)`.

Смягчающее обстоятельство, и существенное: **все три потребителя защищены
поимённо**. `routeMidpoint` пропускает нулевые сегменты (`labelPosition.ts:64`),
`endTangent` / `startTangent` — тоже (`:105, :116`), `isOrthogonal` в тесте
нулевой сегмент считает валидным. То есть симптомы вылечены по одному
вместо общего правила. Требование спецификации «лишних перегибов не рисуем»
(строка 52) визуально выполняется — перегибов действительно нет,
есть лишние точки на прямой.

## Вердикт

**Заявленное «не режется» — на месте полностью.** `routing.ts` (223 строки),
`labelPosition.ts` (119), тесты к обоим, три правки в `ConnectorView` —
всё существует, всё работает. Подпись, которую план 06 разрешал срезать
целиком, **не срезана**: `ConnectorLabel.tsx` написан, ветка коннектора
в `EditingOverlay.tsx` написана, двойной клик открывает ввод. То есть срез
не понадобился вовсе, и полный объём спецификации доехал.

**Девять критериев приёмки из девяти выполнены**, с оговоркой по критерию 7,
переформулированному планом 04 — и переформулированному, на мой взгляд,
корректно: удалить ключ из модели зона A действительно не может, а
подменять задачу удобством исполнителя план как раз отказался.

**Четыре принятые находки плана 06 выполнены все четыре**, и по существу,
а не формально. Селектор действительно плоский `number[]` — проверил
по исходнику `zustand`, поэлементное сравнение работает, цикла перерендеров
нет. Наконечники действительно берут угол из маршрута, включая корректный
частный случай для Безье. Ветка обхода действительно уходит за объединяющую
рамку и правильно ограничена двумя связанными фигурами. «Спиной к спине»
разведено с «лицом к лицу» по знаку, а не по оси, — то есть исправлено
именно то, на что указывал блокирующий пункт ревью геометрии.

**Провалов два, и оба — бумажные.**

Первый: `DECISIONS.md:340-342` **не исправлен**. Это ровно та запись,
из-за которой была затеяна отдельная строка в плане 04 («Отдельно:
исправление ложной записи»), и ровно та, про которую ревьюер интеграции
написал: «если не поправить сейчас, четвёртым будет утренний отчёт».
Ирония замкнулась: подписку сделали, а запись о ней осталась ложной —
она приписывает работу коммиту `54b8d79`, который её не делал, и описывает
подписку «на четыре числа», хотя маршрут длиннее. Плюс по этому прогону
в журнале решений нет ни одной новой записи, хотя решений принято минимум
пять. Это прямое нарушение `CLAUDE.md`.

Второй: запрос напарнику в `CONTRACT-REQUESTS.md` **не написан**. Следствие
не бумажное, а пользовательское: подпись с линии убрать нечем. Стёртый текст
уходит с доски, но секция «Подпись» в инспекторе остаётся навсегда, и вернуть
линию в состояние «подписи нет» невозможно ни с холста, ни из панели.

**Три дефекта геометрии, которых не видит ни один тест** (по возрастанию
неприятности): лишние коллинеарные точки в маршруте — безобидно; холостой
хвост ветки обхода при совпавшей координате вдоль (`top/top` рядом,

разворот сквозь собственную фигуру в перпендикулярной ветке, когда угол
оказывается позади вылета — заметно и неправильно. Все три предсказаны
ревью, все три прошли мимо плана: первый — потому что правило вычистки
не приняли, второй — потому что переписали одну проекцию из двух, третий —

и не вернулась даже после того, как проверка плана её переоткрыла.

Ни один из трёх не роняет приложение и не валит критерии. Все три —
кандидаты в следующий прогон, а не повод не принимать этот.
