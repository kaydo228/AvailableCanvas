**Важно про текст.** У Konva нет редактируемого текста. Приём стандартный: при двойном
клике поверх холста абсолютно позиционируется обычный `<textarea>`, его координаты
считаются из мировых через трансформ вьюпорта, по `blur` значение уезжает в узел, а
`<textarea>` убирается. Пишется за час, но про него надо знать заранее.

## 2.2. Свои — это и есть обязательный пункт «Workflow»

Задание требует **хотя бы один** workflow, применимый к реальной задаче. Делаем два,
по одному на человека — так честнее, чем один на двоих, и роли у вас разные.

**Скилл A — `canvas-node-type`.** Процедура «добавить новый тип объекта на холст».
Ровно то, что A повторит пять раз за неделю: фигура, текст, стикер, картинка, коннектор.
Шаги: тип в `shared/types` → рендерер в `canvas/nodes` → инструмент в `canvas/tools` →
секция в инспекторе → юнит-тест инвариантов → запись в `docs/DECISIONS.md`.

**Скилл B — `feature-slice`.** Процедура «новый слайс в `features/`»: структура папки,
срез стора, публичный `index.ts`, тест, подключение к маршруту, проверка что слайс
не тянет ничего из чужой зоны.

**Файл-workflow `workflows/pre-merge.md`.** Чеклист перед вливанием в `main`:
typecheck → biome → vitest → playwright → `/code-review` → `/simplify` → прогон критериев
приёмки из ТЗ по своей зоне → строка в `REPORT.md`.

**Файл-workflow `workflows/nightly-run.md`.** Полная схема с занятия для крупной фичи
(A прогоняет её на коннекторах в ночь со среды на четверг): спецификация → два независимых
ревьюера по два раунда → план → проверка плана → реализация → тесты → аудит реализации
отдельными агентами → отчёт отдельным файлом.

## 2.3. Superpowers

Ставится одной командой, даёт хуки, которые не дают проскочить этап проектирования.
Ставит **один из вас** и в первый же день, иначе смысла нет.

Перед установкой — два запроса, именно в таком порядке, как в материалах занятия:
сначала «расскажи что это, ничего не ставь», потом «проверь на безопасность: что ставит,
какие хуки, куда ходит по сети; дай вердикт».

# 3. Хуки

Лежат в `.claude/hooks/`, подключены в `.claude/settings.json`. Все требуют `jq`
(`brew install jq`).

| Хук | Событие | Что делает | Зачем в ДЗ |
|---|---|---|---|
| `log-prompt.sh` | `UserPromptSubmit` | дописывает каждый ваш промпт в `sessions/$DEV_NAME/ГГГГ-ММ-ДД.md` | **закрывает бонус «журнал сессий с дословными промптами» автоматически** |
| `guard-secrets.sh` | `PreToolUse` на `Write\|Edit` | запрещает запись в `.env`, `*.key`, `*.pem`, `settings.local.json` | бонус «изоляция», защита от утечки при сдаче |
| `guard-bash.sh` | `PreToolUse` на `Bash` | блокирует `rm -rf /`, `git push --force`, чтение `.env` через терминал | тот самый механизм из C2 |
| `format-file.sh` | `PostToolUse` на `Write\|Edit` | прогоняет `biome check --write` по изменённому файлу | агент перестаёт спорить о форматировании |
| `gate-stop.sh` | `Stop` | typecheck и линт; при провале не даёт закончить сессию | не даёт сдать сломанную ветку |

**Честная оговорка, которую надо записать в `REPORT.md`.** `guard-bash.sh` — это шаблон
на строку команды. Он не остановит `python -c "print(open('.env').read())"`. Проверьте это
руками и запишите: попытка через `cat` отбита, попытка через Python прошла. Это ровно
тот сюжет с занятия, и признать его — плюс к оценке, а не минус.

**Про `gate-stop.sh`.** Хук на `Stop` с кодом 2 не даёт сессии завершиться и отправляет
агента чинить. Две защиты, обе появились не от хорошей жизни:

1. **Файл-марка.** Если тесты падают стабильно, без неё получится петля: агент не может
   закончить, чинит, снова не может закончить. Второй подряд отказ пропускает сессию.
2. **Проверка, что проект вообще существует.** Первая версия хука запускала
   `npm run typecheck` безусловно и блокировала сессию в репозитории, где ещё нет
   `package.json` — то есть в первый же день, до того как B поднимет скелет. Теперь хук
   молча пропускает, если нет `package.json`, нет скрипта `typecheck` или нет конфига
   Biome.

Обе поймались на живом прогоне, а не в теории. Это стоит записать в `REPORT.md`:
хук, который блокирует работу вместо того, чтобы её страховать, — самая частая
судьба таких механизмов.

# 4. MCP

Ставить не обязательно, но два сервера окупаются на этом проекте.

| Сервер | Зачем именно здесь |
|---|---|
| **Playwright MCP** (`npx @playwright/mcp@latest`) | агент сам открывает приложение, кликает по холсту и смотрит результат; для ломателя это разница между «предположил» и «проверил» |
| **Chrome DevTools MCP** (`npx chrome-devtools-mcp@latest`) | профилирование NFR-01: снять реальный fps на 1000 узлов, а не поверить на слово |
| **Context7** | подтягивает свежую документацию Konva и Zustand в контекст; Konva агенты помнят плохо и уверенно выдумывают API |

**Отдельный сюжет для бонуса «изоляция».** Включите `/sandbox` и проверьте границу
двумя способами: запись файла за пределы рабочей папки через терминал и то же самое
через подключённый MCP. Песочница накрывает Bash и дочерние процессы, но не MCP.
Вывод обеих попыток — в `REPORT.md`. Это готовый пункт «изоляция с доказательством».

# 5. CLAUDE.md проекта

Создаётся в день 1 через `/init` и дописывается руками. Минимум, который экономит
больше всего:

- стек и запрещённые альтернативы («рендер только через react-konva, DOM-узлы на холсте
  не создавать, кроме оверлея textarea»);
- границы зон A и B и правило «свою зону не покидать»;
- контракт: `shared/types` и `shared/store` меняются только парой, коммит с префиксом `contract:`;
- инварианты модели из раздела 5 ТЗ — списком, чтобы агент их не ломал;
- «не трогать `.env`, `*.key`, `settings.local.json`»;
- команды: `npm run dev`, `test`, `typecheck`, `lint`, `e2e`.
