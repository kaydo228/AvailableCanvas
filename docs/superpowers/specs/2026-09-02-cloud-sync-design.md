# Синхронизация досок между устройствами

**Дата:** 2026-09-02
**Статус:** утверждено, ждёт плана реализации

## Зачем

Сейчас доски и картинки живут только в IndexedDB того браузера, где их создали.
Открыть свою доску на другом устройстве нечем: единственный перенос — экспорт
`.prostor.json` руками. Нужен аккаунт, за которым доски ходят сами, и публичная
ссылка «только чтение» для тех, кому доску показывают.

Это осознанный выход за границы ТЗ: раздел 1.2 выносил бэкенд и совместную
работу наружу. Совместного редактирования по-прежнему не будет — добавляется
только хранение своих досок и ссылка на просмотр.

## Решения, принятые до дизайна

| Вопрос | Решение | Почему |
|---|---|---|
| Охват | свои доски + публичная ссылка на чтение | совместного редактирования не нужно; ссылка нужна, чтобы показывать |
| Вход | e-mail и пароль | без внешних сервисов и без писем: на бесплатном тарифе встроенная почта шлёт единицы писем в час и уходит в спам |
| Офлайн | локальное хранилище главное, сервер догоняет | доска обязана работать без сети — это свойство продукта, а не деталь |
| Конфликт | побеждает версия с более поздним `updated_at`, целиком | доску правит один человек; слияние по узлам — цена без спроса |
| Провайдер | Supabase | готовые вход, база и хранилище файлов, серверного кода нет, бесплатно без карты |

**Почему не Firebase:** с 3 февраля 2026 Cloud Storage требует тарифа Blaze,
то есть привязанной карты. Картинки нам нужны — вариант перестал быть бесплатным
в нужном смысле.

**Почему не свой сервис на Cloudflare Workers:** пришлось бы писать
аутентификацию руками — хеширование паролей, сессии, сброс. Это худший код,
который можно написать самому, когда рядом лежит готовый.

**Цена выбора Supabase:** бесплатный проект засыпает после семи суток без
запросов, будится кнопкой в панели, а после 90 суток сна теряет адрес API.
Лечится ежедневным пингом по расписанию. Пока сервер спит, приложение работает
на локальной копии — данные не теряются, теряется только синхронизация.

## Границы зон

Новый слайс `src/features/cloud` — зона B (оболочка). `features/canvas` не
меняется вовсе.

Общий шов (`shared/types/document.ts`, `shared/store/`) **не трогается**:
метаданные синхронизации кладутся не в `Project`, а в отдельный стор IndexedDB.

## Данные на сервере

Одна строка на доску: документ целиком в `jsonb`. Делить `projects` и
`documents`, как локально, здесь незачем — список тянется выборкой колонок.

```sql
create table public.projects (
  id          text primary key,
  owner       uuid not null references auth.users on delete cascade,
  name        text not null,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null,
  thumbnail   text,
  document    jsonb not null,
  is_public   boolean not null default false
);

alter table public.projects enable row level security;

create policy "владелец видит своё, остальные — только публичное"
  on public.projects for select
  using (owner = auth.uid() or is_public);

create policy "писать может только владелец"
  on public.projects for all
  using (owner = auth.uid()) with check (owner = auth.uid());
```

`id` — тот же `nanoid`, что и локально. Доска не «переезжает», а получает копию:
после первой выгрузки локальная и удалённая версии — одна и та же доска, и
повторный вход на том же устройстве ничего не задваивает.

Картинки — bucket `images`, путь `owner/blobId`. Писать в свою папку может
только владелец; на чтение bucket публичный. Связывать доступ к файлу с флагом
`is_public` его доски в Storage дорого: `blobId` неугадываем, а публичная доска
и так показывает свои картинки всем, кому дали ссылку.

## Локальные метаданные

Новый стор `sync` в IndexedDB, ключ — `projectId`:

```ts
interface SyncState {
  projectId: Id;
  /** Владелец, за которым закреплена доска. Нет — доска локальная, ничья. */
  owner?: string;
  /** `updated_at` версии, которая точно доехала до сервера. */
  remoteUpdatedAt?: number;
  /** Есть локальные правки, не уехавшие на сервер. */
  dirty: boolean;
}
```

Список проектов показывает доски, у которых `owner` не задан (локальные) или
совпадает с текущим пользователем. Иначе на общем компьютере второй вошедший
увидел бы доски первого.

## Поток синхронизации

**После входа (pull):** выбрать `id, name, updated_at, is_public` всех своих
досок. Для каждой из объединения локальных и удалённых `merge.ts` возвращает
решение — функция чистая и тестируется без сети:

```ts
type Decision =
  | { kind: 'pull' }           // на сервере новее — скачать документ
  | { kind: 'push' }           // локально новее или dirty — выгрузить
  | { kind: 'delete-local' }   // синхронизировалась раньше, на сервере её нет
  | { kind: 'nothing' };
```

**Чьё время сравниваем.** `updated_at` ставит клиент — это то же
`Project.updatedAt`, что уже есть локально. Сервер мог бы ставить своё `now()`,
но тогда локальную версию не с чем сравнивать до выгрузки. Следствие: на
устройстве со сбитыми часами «новее» окажется не та версия. Ограничение
осознанное; правки одного человека на двух устройствах почти никогда не идут
одновременно.

**Локальные доски при первом входе.** Доски без владельца принадлежат
устройству, а не аккаунту, поэтому молча забирать их в аккаунт нельзя: вход
на чужом компьютере утащил бы чужие доски. При первом входе показывается один
вопрос — «перенести N локальных досок в аккаунт?». Согласился — им проставляется
`owner` и они выгружаются; отказался — остаются локальными и вопрос больше
не задаётся (запоминается в `sync`).

**Удаление.** Локальное удаление сносит строку на сервере. Отдельной таблицы
«надгробий» нет: доска, у которой в `sync` есть `remoteUpdatedAt`, а на сервере
её больше нет, удаляется локально. Доска без `remoteUpdatedAt` — та, что ещё
не выгружалась, — не трогается никогда.

**Выгрузка (push).** Через 3 с после последнего автосохранения (у автосохранения
свой дебаунс 500 мс, складывать их в один нельзя — выгрузка на каждый штрих
съест квоту) и при уходе с доски. Порядок внутри одной выгрузки: сначала
картинки, потом документ. Обратный порядок даёт мгновение, когда на сервере
лежит доска со ссылками на ещё не загруженные файлы.

**Картинки.** Выгружаются те `blobId`, что упомянуты в документе и ещё не
уехали. Скачиваются лениво: `getBlob` не нашёл файл локально — идёт в Storage
и кладёт в локальный кэш. Одна точка на всё приложение; `ImageView` и экспорт
о сети не знают.

Уборка осиротевших картинок (`collectOrphanBlobs`) остаётся локальной и считает
по локальным документам. После pull локальные документы повторяют серверные,
поэтому она не снесёт нужное.

## Публичная ссылка

Кнопка «Поделиться» ставит `is_public = true` и даёт адрес `/s/:projectId`.
Маршрут открывает доску без входа и без записи: инструменты, инспектор и
автосохранение выключены, экспорт остаётся. Документ читается напрямую с сервера
и не попадает в локальную базу — чужая доска не должна оседать в списке проектов
у того, кто просто перешёл по ссылке.

## Ошибки и деградация

| Что случилось | Что видит человек |
|---|---|
| Не вошёл | приложение работает как сейчас, полностью локально; ни одного запроса наружу |
| Сети нет | правки копятся, `dirty: true`, индикатор: «сохранено локально» |
| Проект Supabase спит | то же самое: ошибка сети, локальная работа не прерывается |
| Кончилась квота | тост с прямой причиной, выгрузка останавливается, локально всё цело |
| Вход не удался | форма показывает ответ сервера, доски на устройстве не трогаются |

Правило одно: **ни одна ошибка сети не может испортить локальные данные.**
Выгрузка и скачивание — операции поверх готового локального состояния, а не
вместо него.

## Проверки

- `merge.test.ts` — таблица «локальное состояние × удалённое → решение»,
  включая доску без `remoteUpdatedAt` (не удалять) и равные времена (ничего).
- Тесты выгрузки и скачивания на подменённом клиенте: порядок «картинки, потом
  документ», повторная выгрузка не плодит копий, ошибка сети оставляет `dirty`.
- E2e: вход, выход, режим `/s/:projectId` (клиент подменяется на заглушку —
  в e2e сети не будет).
- **Существующий тест придётся уточнить.** `e2e/smoke.spec.ts` проверяет
  критерий 12 ТЗ: «после загрузки доска не ходит в сеть». Он станет «**без
  входа** доска не ходит в сеть». Обещание из README сужается — это надо
  написать прямым текстом в README и в `docs/DECISIONS.md`, а не тихо
  переписать тест.

## Что делает человек руками

1. Завести проект в Supabase (бесплатный тариф, карта не нужна).
2. Выполнить SQL из этой спеки в их редакторе, создать bucket `images`.
3. Положить `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` в `.env.local` —
   файл под защитой хука `guard-secrets.sh`, агент в него не пишет.
4. Те же две переменные — в настройки хостинга.
5. Включить ежедневный пинг, чтобы проект не засыпал.

Без этих переменных приложение собирается и работает в нынешнем локальном
режиме: кнопки входа просто нет. Это же и режим разработки по умолчанию.

## Чего не делаем

Реального времени и совместного редактирования, комментариев, истории версий
на сервере, корзины, шифрования на клиенте, приглашений, прав «на запись
по ссылке» и повторного вопроса о переносе локальных досок, если один раз
на него уже ответили «нет».

## Риски

1. **Пауза бесплатного тарифа.** Семь суток без запросов — проект спит.
   Смягчено пингом и офлайн-first; полностью снимается только платным тарифом.
2. **Квоты:** 500 МБ базы и 1 ГБ файлов. Доска на тысячу узлов — сотни
   килобайт `jsonb`; упрутся раньше картинки. Предел на файл (10 МБ) уже есть.
3. **Anon-ключ виден в собранном фронтенде.** Так и задумано: он публичный,
   и вся защита держится на правилах доступа в базе. Значит правила — это
   граница доверия, и ошибка в них — это утечка чужих досок. Проверять их
   отдельно, а не «на глаз».
4. **Обещание «данные никуда не уходят»** перестаёт быть безусловным.
   Формулировка в README меняется вместе с кодом, в том же коммите.
