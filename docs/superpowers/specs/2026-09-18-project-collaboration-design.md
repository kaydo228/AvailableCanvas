# Приглашения и совместная работа над проектом

**Дата:** 2026-09-18
**Статус:** утверждено, ждёт плана реализации

## Зачем

Сейчас владелец может открыть доску всем по публичной ссылке, но это только
анонимный просмотр. Нужен управляемый доступ конкретным людям: приглашение по
email, роли «редактор» и «просмотр», список участников и обновление открытой
доски без перезагрузки страницы.

Автосохранение остаётся. Промежуточный индикатор «Сохранение…» убирается,
поскольку при частых совместных правках он постоянно мигает. Состояния,
которые требуют внимания — ошибка, конфликт, удаление и «только локально» —
остаются видимыми.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Кого можно пригласить | любой email, включая ещё не зарегистрированный |
| Роли | `editor` и `viewer`; владелец остаётся отдельной ролью |
| Письмо новому пользователю | стандартное приглашение Supabase Auth через Edge Function |
| Уже зарегистрированный пользователь | доступ выдаётся сразу; отдельное письмо пока не отправляется |
| Обновления | Supabase Realtime, без перезагрузки страницы |
| Одновременная правка одного объекта | побеждает последнее сохранение всей доски |
| Защита | RLS в Postgres; UI лишь отражает права, но не является границей безопасности |
| Индикатор записи | не показывать переходное `saving`; показывать только полезные устойчивые состояния и ошибки |

### Почему этот вариант

Рассматривались три подхода:

1. **Realtime поверх существующей строки `projects` — выбран.** Минимально
   меняет текущую офлайн-first модель и даёт мгновенное обновление. Цена —
   последнее сохранение побеждает при одновременной правке одного объекта.
2. **События по каждому действию.** Лучше сливает независимые изменения, но
   требует нового журнала операций, серверной дедупликации и восстановления
   состояния из событий.
3. **CRDT (например, Yjs).** Даёт поведение уровня Figma при одновременной
   правке, но заменяет модель документа, историю и сохранение. Для первой
   версии совместной работы это несоразмерно.

Выбранный предел должен быть честно виден в документации: это realtime и роли,
но не бесконфликтное редактирование одного объекта двумя людьми.

## Данные

### Участники

```sql
create type public.project_role as enum ('editor', 'viewer');

create table public.project_members (
  project_id text not null references public.projects(id) on delete cascade,
  user_id uuid not null references auth.users(id) on delete cascade,
  role public.project_role not null,
  created_at timestamptz not null default now(),
  primary key (project_id, user_id)
);
```

Владелец не дублируется в `project_members`: источником истины остаётся
`projects.owner`. Один пользователь не может иметь две роли в одном проекте.

### Ожидающие приглашения

```sql
create table public.project_invites (
  id uuid primary key default gen_random_uuid(),
  project_id text not null references public.projects(id) on delete cascade,
  email text not null,
  role public.project_role not null,
  invited_by uuid not null references auth.users(id) on delete cascade,
  created_at timestamptz not null default now(),
  unique (project_id, email)
);
```

Email хранится нормализованным (`lower(trim(email))`). Повторное приглашение
того же адреса обновляет роль и повторно отправляет приглашение, если аккаунта
ещё нет. После принятия строка удаляется.

`projects` получает два служебных поля:

```sql
alter table public.projects
  add column revision bigint not null default 0,
  add column updated_by uuid references auth.users(id) on delete set null;
```

`revision` растёт при каждой удалённой записи. `updated_by` позволяет клиенту
не применять обратно собственное событие Realtime.

## Правила доступа

RLS разрешает:

- владельцу — читать, редактировать, удалять проект и управлять участниками;
- `editor` — читать и обновлять `name`, `document`, `thumbnail`, `updated_at`,
  `revision` и `updated_by`, но не владельца и не публичность;
- `viewer` — только читать;
- анониму — читать только проект с `is_public = true`, как сейчас.

Проверки членства оформляются небольшими `security definer`-функциями в
закрытой схеме `private`. Это избегает рекурсивных RLS-политик между
`projects` и `project_members`. Выполнение вспомогательных функций выдаётся
только нужным ролям; `service_role`/secret key никогда не попадает во фронтенд.

Storage получает те же права на картинки проекта: владелец и редактор могут
читать и загружать, зритель может читать. Публичный режим остаётся отдельным.

## Приглашение

### Edge Function `invite-project-member`

Функция принимает `{ projectId, email, role }` и токен текущей сессии.

1. Проверяет пользователя по JWT.
2. Проверяет, что он владелец проекта.
3. Нормализует email и запрещает приглашать самого владельца.
4. Если аккаунт уже существует, сразу создаёт/обновляет `project_members`.
5. Если аккаунта нет, создаёт `project_invites` и вызывает
   `auth.admin.inviteUserByEmail()` с разрешённым redirect URL приложения.
6. Возвращает одно из состояний: `member-added`, `invite-sent` или безопасную
   ошибку без утечки сведений о чужих проектах.

Функция использует серверный secret key Supabase. Он хранится только в secrets
Edge Functions. Адрес приложения хранится в `APP_URL`; произвольный redirect
из запроса не принимается.

### Принятие

При подтверждении письма Supabase создаёт сессию и возвращает пользователя на
маршрут `/invite`. Экран предлагает задать пароль, затем вызывает RPC
`accept_my_project_invites()`. RPC сопоставляет подтверждённый email текущего
пользователя с ожидающими приглашениями, создаёт членство и удаляет ожидание.
После этого приложение открывает приглашённый проект.

При обычном входе тот же RPC вызывается один раз: так истёкшая ссылка или вход
с другого устройства не оставят уже подтверждённое приглашение навсегда.

## Интерфейс управления доступом

Кнопка «Поделиться» открывает диалог с тремя зонами:

1. email + выбор роли + «Пригласить»;
2. текущие участники с изменением роли и удалением;
3. существующая публичная ссылка и кнопка закрытия публичного доступа.

Диалог управления доступом видит только владелец. Редактор видит короткую
метку «Совместный проект», зритель — «Только просмотр». У зрителя отключены
инструменты холста, инспектор, горячие клавиши изменения и автосохранение;
экспорт остаётся доступен.

После отправки формы показывается точный результат: «Приглашение отправлено»
или «Доступ добавлен». Ошибки формы остаются в диалоге и дублируются тостом
только для сетевых сбоев.

## Список проектов и локальная копия

После входа клиент запрашивает все строки `projects`, доступные по RLS, а не
только `owner = auth.uid()`. Роль определяется по `projects.owner` и
`project_members` и сохраняется в локальном `SyncState` как
`owner | editor | viewer`.

Совместный проект получает локальную IndexedDB-копию, поэтому его можно
открыть при кратком обрыве сети. Только владелец и редактор могут пометить её
`dirty` и отправить на сервер. Локальная копия зрителя обновляется из Realtime,
но никогда не выгружается.

Удаление участника закрывает Realtime-канал, удаляет локальную копию из списка
и переводит уже открытый экран в понятное состояние «Доступ отозван».

## Realtime

Таблица `projects` добавляется в публикацию `supabase_realtime`. На открытом
совместном проекте клиент подписывается на `UPDATE` и `DELETE` только этой
строки. RLS Supabase применяется и к событиям. Для немедленного отзыва доступа
используется отдельное приватное событие `access-revoked` в персональном канале
участника: после удаления membership обновление самой строки проекта уже не
может пройти его RLS. Событие отзыва не содержит документ или другие данные
проекта и заставляет клиент закрыть оба канала.

При чужом `UPDATE` клиент:

1. проверяет, что `revision` новее локальной;
2. чинит входящий документ через существующий `repairDocument`;
3. заменяет документ в store без запуска обратного автосохранения;
4. обновляет IndexedDB и `SyncState`;
5. сохраняет текущий viewport пользователя, чтобы чужая камера не дёргала его
   экран.

При локальном сохранении `revision` увеличивается атомарно на сервере. Событие
с собственным `updated_by` игнорируется. При разрыве websocket клиент
переподписывается штатным механизмом Supabase и после восстановления делает
обычный pull, чтобы закрыть пропущенное окно.

Одновременно передаются только сохранённые состояния, не курсоры и не
промежуточные точки каждого движения. Presence и чужие курсоры в эту версию не
входят.

## Автосохранение без «загрузки»

Статус `saving` остаётся внутренним: он нужен cloud sync, но
`SaveIndicator` ничего для него не рисует. После успешной записи можно
показывать спокойное «Сохранено» только если оно уже предусмотрено текущим
интерфейсом; никакого спиннера и мигания на каждую правку нет.

Статусы `error`, `conflict`, `deleted` и `local-only` остаются видимыми. Это не
декоративная загрузка, а информация о риске потери или несинхронизированных
данных.

## Ошибки и граничные случаи

| Ситуация | Поведение |
|---|---|
| Email уже участник | обновить роль, не создавать дубль |
| Email владельца | отказ с понятным текстом |
| Истёкшее письмо | повторная отправка владельцем |
| Зритель пытается записать напрямую | RLS возвращает отказ; локальный store не предлагает действие |
| Доступ отозван во время работы | закрыть канал, прекратить сохранение, показать экран «Доступ отозван» |
| Сеть пропала у редактора | продолжить локально, показать «Сохранено только здесь», отправить после восстановления |
| Два редактора сохранили одновременно | большая `revision` побеждает; локальная непринятая версия остаётся экспортируемой до подтверждения замены |
| Edge Function недоступна | членство не меняется; форма остаётся заполненной для повтора |

## Проверки

- SQL-тесты RLS: владелец, редактор, зритель, посторонний и аноним для каждой
  операции над `projects`, `project_members` и `project_invites`.
- Unit-тесты ролей и переходов sync-состояния.
- Тест Edge Function: только владелец приглашает; новый email получает invite;
  существующий получает membership; повтор меняет роль без дубля.
- E2E: приглашение, принятие новым аккаунтом, смена роли, отзыв доступа,
  viewer без инструментов и editor с записью.
- E2E с двумя страницами: изменение редактора приходит владельцу без reload;
  собственное событие не создаёт цикл сохранений; viewport не прыгает.
- Регрессия индикатора: при обычном автосохранении нет «Сохранение…», ошибки и
  `local-only` по-прежнему видимы.
- Полный `npm run check`; отдельные SQL-тесты выполняются через Supabase CLI.

## Ручная настройка после реализации

1. Связать репозиторий с проектом `wfhxobnovnhsimnfnefb` через Supabase CLI.
2. Применить миграцию базы.
3. Добавить GitHub Pages URL в разрешённые Auth redirect URLs.
4. Задать Edge Function secret `APP_URL` равным адресу приложения.
5. Задеплоить `invite-project-member`.
6. Убедиться, что `projects` включена в Realtime publication.

## Не входит в эту версию

- CRDT/операционное слияние одновременных правок;
- чужие курсоры, выделения и Presence;
- комментарии, чат и история версий;
- передача владения;
- отдельное письмо уже зарегистрированному пользователю;
- публичная ссылка с правом редактирования.
